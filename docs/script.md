# 발표 대본

`presentation.md`의 슬라이드 순서에 맞춘 발표 대사입니다. 총 5~10분 기준으로, 섹션별 예상 시간을 같이 표시했습니다. 그대로 읽으셔도 되고, 본인 말투로 편하게 바꾸셔도 됩니다.

---

### 인트로 (10초)

"안녕하세요, 저는 은행 계좌 사기 탐지 모델을 만드는 MLOps 미니 프로젝트를 진행했습니다. 데이터 준비부터 학습, 실험 기록, 재현 가능한 실행 환경까지 만든 과정을 공유드리겠습니다."

---

### 1. 문제 정의 (1분)

"먼저 어떤 문제를 풀었는지 말씀드릴게요. 은행에 새 계좌를 만들겠다는 신청이 들어오면, 그 신청이 사기인지 정상인지를 자동으로 판별하는 모델을 만들었습니다.

데이터는 Feedzai가 NeurIPS 2022에 공개한 Bank Account Fraud 데이터셋의 Base 버전을 썼고요, 100만 건의 계좌 개설 신청 각각에 소득, 나이, 사용한 기기, 신청 속도 같은 정황 정보 30개가 붙어있습니다. 이 정보만 보고 사기 여부를 맞히는 게 목표입니다.

여기서 가장 중요한 특징은, 사기가 전체의 1.1%뿐이라는 겁니다. 11,029건이요. 그래서 이 문제는 단순히 정확도를 높이는 문제가 아니라, 희귀한 사기를 놓치지 않으면서도 정상 고객을 너무 많이 오탐하지 않는 균형점을 찾는 문제입니다."

---

### 2. 평가 지표 (1~2분)

"이렇게 극단적으로 불균형한 데이터에서는 accuracy, 그러니까 정확도를 쓰면 안 됩니다. 전부 정상이라고만 찍어도 98.9%가 나오거든요. 그래서 이번 프로젝트에서는 accuracy를 아예 쓰지 않기로 했습니다.

대신 두 가지 지표를 썼습니다. 주지표는 TPR@FPR5%입니다. [그림/화면 가리키며] 이 그림처럼, 정상 고객을 사기로 잘못 판단하는 비율, 즉 FPR을 5% 이내로 제한했을 때, 실제 사기 중 몇 %를 잡아내는지를 보는 지표입니다. 은행 입장에서 '오탐은 이 정도까지만 감내하겠다'는 현실적인 제약 아래에서 성능을 보는 거죠.

보조지표로는 AUPRC를 썼고요, 이건 불균형 데이터에서 흔히 쓰이는 종합 지표입니다.

결과를 보면, LightGBM 기본값으로 학습한 베이스라인이 TPR@FPR5%는 0.503, AUPRC는 0.154가 나왔습니다. 정상 고객 오탐을 5% 이내로 묶은 상태에서 사기의 절반 정도를 잡아낼 수 있다는 뜻이고, 이 화면은 실제로 MLflow에 기록된 값입니다."

---

### 3. 시간 분할 전략 (1~2분)

"데이터에는 8개월치 기록이 있는데요, 이걸 무작위로 섞어서 나누지 않고 시간 순서대로 잘랐습니다. 0월부터 5월까지는 학습에, 6월은 검증에, 7월은 아예 이번 주차에서는 쓰지 않고 남겨뒀습니다. 나중에 드리프트 실험용으로 쓸 예정이라서요.

왜 무작위로 안 섞었냐면, 실제 서비스는 과거 데이터로 학습해서 미래를 예측하는 상황이기 때문입니다. 무작위로 섞으면 학습 데이터 안에 미래 정보가 살짝 섞여 들어가서, 검증 성능이 실제보다 부풀려 보이는 착시가 생길 수 있습니다.

그리고 이 표를 보시면, 검증·테스트 구간의 사기 비율이 학습 구간보다 오히려 높습니다. 그래서 검증 성능이 학습 때보다 낮게 나오는 게 정상이라는 걸 미리 예상하고 시작했고, 실제로 그 패턴대로 결과가 나왔습니다."

---

### 4. 아키텍처 (1~2분)

"전체 구조는 데이터에서 시작해서 학습, 레지스트리, 서빙, 모니터링, 재학습으로 이어지는 순환 구조로 설계했습니다. [다이어그램 가리키며] 실선으로 표시된 데이터부터 MLflow 레지스트리까지가 이번 주차에 구현을 완료한 부분이고, 점선으로 표시된 서빙, 모니터링, 재학습은 6주차, 7주차에 이어서 만들 예정입니다.

그리고 이 구조를 실제로 어떻게 돌렸냐면, [두 번째 다이어그램 가리키며] Docker Compose로 학습 컨테이너와 MLflow 서버 컨테이너를 분리해서 띄웠습니다. 학습 컨테이너는 한 번 실행되고 끝나지만, MLflow 서버 컨테이너는 계속 떠서 기록을 받아줍니다. 재밌는 건, 이걸 위해서 학습 코드를 한 줄도 안 고쳤다는 겁니다. 환경변수 하나만 바꿔서 '로컬 파일에 저장'과 '서버로 전송'을 전환했습니다."

---

### 5. 툴스택 (2분)

"사용한 툴들을 간단히 말씀드리면요, Python과 pandas로 데이터를 다뤘고, 모델은 과제 규약대로 LightGBM 기본값을 썼습니다. 부스팅 계열 모델이 불균형 데이터에 강하고, 범주형 컬럼을 원-핫 인코딩 없이 자체 처리할 수 있어서 전처리 코드가 단순해지는 장점이 있습니다.

전처리 결과는 parquet으로 저장했는데, CSV와 달리 category 타입 같은 스키마 정보가 그대로 보존되기 때문입니다.

실험 기록은 MLflow를 썼고요, 하이퍼파라미터나 시간분할 설정 같은 params와 TPR@FPR5%, AUPRC 같은 metrics를 자동으로 기록해줍니다.

실행 환경은 Docker와 Docker Compose로 관리했습니다. Docker는 OS나 시스템 라이브러리까지 통째로 포장해서 재현성을 확보하고, Compose는 역할이 다른 컨테이너 여러 개를 함께 띄우고 연결하는 데 썼습니다.

그리고 설정값은 conf 폴더의 yaml 파일로, 코드와 분리해뒀고요, pytest로 전처리 로직이 규약대로 동작하는지 검증했습니다.

이 모든 선택의 기준은 하나였습니다. '재현 가능하고, 검증 가능한가.'"

---

### 6. 구현 결과 (1~2분)

"필수 구현 요구사항을 하나씩 확인해보면, 학습 코드는 노트북이 아니라 preprocess, train, evaluate 세 개의 스크립트로 분리했고, Docker 컨테이너 안에서 전처리부터 학습까지 1회 실행에 성공했습니다. 로컬에서 직접 돌린 결과와 완전히 동일한 성능이 나오는 것도 확인했는데, 이게 재현성이 확보됐다는 증거입니다. MLflow에도 params와 metrics가 모두 기록된 run이 남아있습니다.

선택 과제 중에는 세 가지를 같이 진행했는데요, 먼저 pytest로 단위 테스트 14개를 작성했습니다. [화면 가리키며] 재밌는 경험이 있었는데, 일부러 시간 분할 로직에 버그를 심어봤더니, 처음엔 테스트 데이터가 그 경계 상황을 커버하지 못해서 못 잡아내더라고요. 테스트 데이터에 경계값을 추가하고 나서야 정확히 잡아냈습니다. 테스트 로직 자체뿐 아니라, 테스트 데이터가 실제 상황을 얼마나 잘 커버하는지도 중요하다는 걸 배웠습니다.

그다음엔 conf 폴더로 설정값을 코드에서 분리했고, 리팩터링 전후로 테스트가 계속 통과하는 걸 확인해서 안전하게 진행했습니다.

마지막으로 Docker Compose로 학습 컨테이너와 MLflow 서버 컨테이너를 분리하는 구조를 만들었습니다."

### 7. 전처리 규칙 (1분, 시간 부족하면 생략 가능)

"전처리에서 신경 썼던 부분을 짧게 말씀드리면요, 이 데이터셋은 '모른다'는 정보를 NaN이 아니라 -1이라는 숫자로 숨겨서 표시해뒀습니다. 이걸 그대로 두면 모델이 -1을 진짜 숫자로 착각하기 때문에, 5개 컬럼에서 -1을 진짜 결측치로 바꿨고요. intended_balcon_amount라는 컬럼은 규칙이 달라서 음수 전체를 결측으로 처리했습니다. 반대로 credit_risk_score나 velocity_6h는 음수가 정상적인 신호라서 그대로 뒀습니다. 이 규칙들이 실제 데이터와 맞는지 하나하나 검증하면서 진행했습니다."
